# scene — контракт 6 (v1.2): сцена, которую отдаёт 2D-редактор

Граница: editor2d (Алексей, `Project/frontend/editor2d/`) **→** matching (Артём), simulation (Стас), хранение проекта.
Полный пример: [scene.example.json](scene.example.json).
Заменяет черновик [topology.md](topology.md) / [topology.py](topology.py), что поменялось — в конце.

Контракт описывает **только то, что редактор отдаёт наружу**. Состояние вида (зум, панорама,
выделение, сетка, цвета) в контракт не входит и хранится во фронте. Формат таймлайна — отдельный
контракт Стаса; с этим контрактом он связан только через `id` роботов и точек.

## Общие правила

- **Единицы — метры.** Все координаты сразу в метрах сцены. Пересчёт в пиксели делает редактор
  при отрисовке, наружу пиксели не уходят (поле `scale_m_per_unit` убрано).
- **Система координат `y_down`:** начало в левом верхнем углу плана, X вправо, Y вниз (как в canvas/Konva).
  Если бэкенд считает с Y вверх — нужно перевернуть: `y' = site.height - y`.
- **Углы** в градусах, 0° — вдоль +X, положительное направление — по часовой стрелке (тоже как в Konva).
- **Точка:** `{ "x": float, "y": float }`.
- **Полигон** — от 3 вершин, **не замкнут** (первую вершину в конце не повторяем).
- **`id`** — строка, уникальна **в пределах всей сцены** (а не только своего списка), не меняется
  после создания. На неё ссылаются другие объекты сцены и таймлайн.
- **`tags`** — свободные пользовательские метки, у всех сущностей; на логику никто не обязан опираться.
- **`categories`** — у зон и ключевых точек: `id` категорий из справочника Артёма, по ним matching
  подбирает оборудование. Может быть пустым. Справочник сейчас собирается из `Книга1.xlsx` скриптом
  `tools/categories_from_xlsx.py` в `frontend/editor2d/src/catalog/categories.json`. В таблице нет своих id,
  поэтому id — транслитерация названия (`Зона хранения` → `zona_hraneniya`). Если Артём заведёт
  свои id, редактор перейдёт на них.
- Необязательное поле передаётся как `null` или не передаётся вовсе; списки — всегда `[]`, не `null`.

## Site

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| width, height | float | да | Габариты плана, м (рамка холста) |
| boundary | list[Point] | да | Контур объекта; для прямоугольного — 4 угла рамки |
| background | Background \| null | нет | Подложка — скан/картинка плана |

**Background:** `image_url: str`, `x, y, width, height: float` (где лежит картинка в метрах сцены),
`opacity: float 0..1`. Нужна только для отрисовки, бэкенду не нужна.
`image_url` — обычный адрес или `data:` URL: картинку, загруженную с компьютера, редактор встраивает
прямо в сцену (JPEG, не больше 2000 px по длинной стороне), потому что сервера для файлов у него нет.
Если хранить сцены на сервере, такие картинки лучше вынести в отдельные файлы и заменить на адрес.

**На платформе (2026-09-24) это уже реализовано на уровне API, не контракта**: `POST
/api/projects/{id}/scene/background` принимает файл подложки и возвращает `image_url` — постоянную
ссылку. API-слой фронта (Владимиров) обязан подменить `data:` URL из редактора на эту ссылку перед
`PUT /scene`, чтобы снапшот проекта не раздувался мегабайтными строками; в сохранённых на платформе
проектах `image_url` всегда обычная ссылка, не `data:`. Сам редактор для автономного `.bat`-дистрибутива
без сервера продолжает встраивать `data:` как раньше — контракт это по-прежнему не запрещает,
переключение — забота API-интеграции, а не `editor2d`.

## Wall

Стена — препятствие: роботы через неё не проходят. Задаётся осью (ломаной) и толщиной.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| id | str | да | |
| name | str | да | Подпись на плане |
| points | list[Point] | да | Ось стены, ≥ 2 вершин; стена занимает полосу `thickness` вокруг оси |
| thickness | float > 0 | да | Толщина, м (по умолчанию 0.2) |
| tags | list[str] | да | |

Проёмы (двери, ворота) — это разрывы между стенами: стену рисуют отдельными участками.
Файлы v1.0/v1.1 без поля `walls` читаются как сцена без стен.

## ChargingPoint

То же, что OperationPoint, плюс:

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| slots | int ≥ 1 | да | Сколько роботов заряжается одновременно |

`categories` тут тоже есть — например, тип зарядки, чтобы matching проверял совместимость с роботом.

## Route

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| id | str | да | |
| name | str | да | |
| points | list[RoutePoint] | да | Ломаная, ≥ 2 вершин |
| bidirectional | bool | да | `true` — ездить можно в обе стороны, `false` — только по порядку `points` |
| tags | list[str] | да | |

**RoutePoint:** `x, y: float` + необязательный `ref: str` — `id` ключевой точки, если вершина
к ней привязана (в редакторе — «примагничена»). Вершины разных маршрутов с одинаковыми
координатами считаются соединёнными (редактор при привязке ставит координаты точно совпадающими).
Так из маршрутов можно собрать граф, не угадывая по геометрии, какой маршрут к какой точке ведёт.

## Проверки, которые делает редактор перед отдачей

Реализованы в `frontend/editor2d/src/scene/validate.ts`. **Ошибки** — сцена нарушает контракт; скачать такую сцену
можно только после явного подтверждения. **Предупреждения** — формально допустимо, но скорее всего ошибка на плане.

Ошибки:
- `id` не уникален в пределах сцены;
- у зоны меньше 3 вершин или контур самопересекается; у маршрута или стены меньше 2 вершин;
- толщина стены не больше 0;
- ссылки ведут в никуда: `zone_id` (на зону), `ref` и `start_point_id` (на ключевую точку),
  `home_charging_point_id` (на точку зарядки);
- `slots` не целое число ≥ 1;
- у робота не задан `category` или это категория не вида «оборудование».

Предупреждения:
- зона, стена, точка, вершина маршрута или робот за границей `site.boundary`;
- точка или робот внутри зоны `restricted`, маршрут проходит через неё;
- маршрут проходит сквозь стену (ближе к оси стены, чем половина толщины); точка или робот стоит в стене;
- категории нет в справочнике или она не того вида (например, оборудование назначено зоне).

## Что поменялось относительно topology.py

| Было | Стало | Зачем |
|---|---|---|
| `scale_m_per_unit` | всё в метрах, `units`, `coordinate_system` | масштаб — это состояние вида редактора, а не данные сцены |
| `operation_points` с `kind` | `operation_points` + `charging_points` | у зарядки свои поля (`slots`), и в ТЗ они показываются отдельно |
| у точек только `tags` | `categories` + `tags` | матчинг смотрит только в `categories`, пользовательские метки его не засоряют |
| — | `name` у зон, точек, маршрутов, роботов | подписи на плане и в проигрывании |
| — | `zone_id` у точек | не нужно пересчитывать попадание в полигон на каждой стороне |
| `Route.points: list[Point2D]` | `RoutePoint` с `ref`, `bidirectional` | привязка маршрутов к точкам → граф для симуляции |
| `RobotPlacement` без ориентации | `start_heading_deg`, `start_point_id`, `home_charging_point_id` | стартовое состояние робота целиком |
| — | `site` (рамка, контур, подложка) | «план объекта» тоже часть сцены |
| — | `schema_version`, `name`, `updated_at` | версионирование и хранение |
| у зон только `tags` | `categories` + `tags` (v1.1) | зоне тоже назначаются место, задачи и условия среды из справочника |
| `catalog_item_id` обязателен | `category` + `catalog_item_id: str \| null` (v1.1) | пользователь ставит вид оборудования, модель подбирается потом |
| — | `walls` (v1.2) | стены — препятствия на плане; симуляции нужно знать, где роботы проехать не могут |
