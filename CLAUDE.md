# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Статус репозитория

Репозиторий разложен на две верхнеуровневые папки:

- **`Project/`** — весь код и «живые» контракты: `Project/backend/contracts/` (контракты данных, без API/БД) + `Project/backend/simulation/` (реализация контракта 7 — событийная симуляция сцены, см. раздел «Симуляция» ниже) + `Project/backend/matching/` (реализация контракта 5 — подбор и explainable-ранжирование, см. раздел «Подбор и ранжирование: matching» ниже), `Project/frontend/` (все экраны платформы, React 19 + TS; 2D-редактор плана объекта, React + Konva, контракт 6 — модуль этого же приложения `src/features/planEditor/`, шаг 7 визарда; до 2026-09-25 был отдельным Vite-приложением `editor2d/`) с контрактом сцены `Project/scene.md`/`Project/scene.example.json` на уровне `Project/`. `Project/архив/` — вытесненные версии тех же модулей, см. раздел «История» ниже.
- **`Документация/`** — справочные и проектные материалы без кода, по зонам ответственности (`общее/` + по папке на каждую предметную область). У каждой зоны — короткий `README.md`-указатель на канонические файлы в `Project/`, без дублирования; общий индекс — `Документация/README.md`.

`Документация/общее/` — референсные материалы хакатона:

- `1. ФЦ БАС.pdf` — основное ТЗ: «Разработка платформы подбора роботизированных решений с расчетом экономического эффекта и визуализацией работы роботов на объекте» (кейс Федерального центра беспилотных авиационных систем, конкурс 2026 г.).
- `Дополнения для участников.pdf` — уточнения и допущения к ТЗ (финансирование, CAPEX/OPEX, каталог, справочник типов роботов).
- `Диаграмма модулей.drawio` (+ `.png` рендеры) — модульная схема решения и таблица контрактов (вкладка «Контракты»), первоисточник для `Project/backend/contracts/`.

По мере появления реального кода (API-слой, БД, docker-compose) этот файл нужно дополнять разделами о командах сборки/запуска/тестов. Ниже — бриф по требованиям ТЗ, которым должна руководствоваться реализация, и описание уже существующих контрактов и фронтенд-модулей.

Своего `categories.json` у редактора с 2026-09-25 нет — он получает общий справочник пропсом. Третьим аргументом скрипту передаётся `Project/книга2.xlsx` (2026-09-25: заменил прежний `артём-стас.ods`, архивирован в `Project/архив/` — та же таблица Артёма, но разложенная по укрупнённым категориям: колонки «Обобщённая категория» / «Подкатегория» / «Исходное название категории») — из «Обобщённой категории» берётся поле `group`, по которому редактор разбивает оборудование в палитре и в выпадающем списке вида робота. У книга2.xlsx также есть категории, которых нет в `Книга1.xlsx` (в основном БАС/морские/сельхоз/строительные задачи) — скрипт их не подхватывает, список категорий по-прежнему строится из `Книга1.xlsx`; 25 из них (реально новые семейства техники, не опечатки) добавлены вручную как `EXTRA_EQUIPMENT_CATEGORIES` в скрипте — источник `Датасет/Датасет/catalog_export_v4.csv` (223 реальных продукта хакатона).

2026-09-25: категорий без группы («Без раздела») больше не бывает. У 12 категорий вида зона/точка/задача/условие среды, которых нет в `книга2.xlsx` (зона ТО/мойки/ожидания/стоянки/маневрирования/уборки, открытая/закрытая зона, холод, влажность, стерильность, взрывоопасность), группа по умолчанию — «Задачи и зоны применения» (`FALLBACK_GROUP` в скрипте), та же, где их уже сгруппированные соседи. А 49 категорий `applies_to = "характеристика"` — это вообще не категории для палитры (решение Стаса по итогам разговора с пользователем: «зона — это как характеристика прибора»), а атрибуты оборудования (грузоподъёмность, тип тары, требования к навигации/покрытию, тип объекта эксплуатации) — скрипт выносит их из `categories.json` в отдельный `backend/contracts/dictionaries/characteristics.json` вместе с вручную подобранным соответствием «категория оборудования → её характеристики» (`EQUIPMENT_CHARACTERISTICS` в скрипте, все 64 вида оборудования):

```bash
cd Project
python tools/categories_from_xlsx.py Книга1.xlsx - книга2.xlsx \
  --dictionary=backend/contracts/dictionaries/categories.json \
  --characteristics=backend/contracts/dictionaries/characteristics.json
```

`--dictionary` выгружает тот же справочник в форме, принятой в визарде (разделами: `equipment_categories`, `working_zones`, `point_kinds`, `tasks`, `environments`) — это общий файл для формы, редактора и бэкенда, тоже только из скрипта. У категории два поля названий: `id` (главное) и `aliases` (как ту же категорию называют в другом справочнике); таблица соответствий лежит в `EXTERNAL_IDS` внутри скрипта и сверяется при генерации, чтобы опечатка не разорвала связь формы и плана.

Второй аргумент `-` — не писать прежний плоский список для отдельного редактора (его больше нет). `--characteristics` — справочник для каталога/matching, не для редактора плана (редактор атрибуты оборудования не показывает). Назначение категория → характеристики подобрано вручную по описанию/назначению, а не выведено из таблиц Артёма механически — при появлении в `Книга1.xlsx` нового вида техники ему нужно завести запись в `EQUIPMENT_CHARACTERISTICS`, иначе скрипт остановится (сверяет ссылки в обе стороны: неизвестная характеристика и оборудование без записи в таблице).

## Архитектура: контракты между модулями (`Project/backend/contracts/`)

Реализация разбита на модули по границам между участниками команды; `Project/backend/contracts/__init__.py` — единая точка входа, документирующая все 9 контрактов и направление каждого (кто → кому). Прежде чем менять любую модель данных, проверь, чей это контракт и кто на другом конце границы:

1. **CatalogItem** (`catalog.py`) — Артём → Стас. Карточка позиции каталога: `identification`/`technical`/`infrastructure`/`economics`/`applicability`/`data_quality` — обязательные группы полей из раздела «Каталог решений» ниже. `tags`/`attributes` — намеренно схемо-свободные словари: новая характеристика или новый тип решения добавляется как данные, а не как новое поле модели.
2. **CompatibilityRule** (`compatibility.py`) — Артём → Стас (эвалюатор в matching). Плоская таблица правил `если условие на оборудовании и условие на объекте → вердикт`, а не дерево связей — это осознанный MVP-выбор. Каждое правило обязано нести `reason` для explainable-ranking.
3. **EconInput/EconOutput** (`econ_io.py`) — Александра → Стас (econWrapper). Единственный контракт на голых `dataclass`, без pydantic/FastAPI: Александра пишет чистые функции расчёта экономики и не должна зависеть от остального стека. `econWrapper` — адаптер, конвертирующий `ScenarioInput → EconInput` и `EconOutput → EconomicsResult` на границе API.
4. **ProjectInput** (`project_input.py`) — Владимиров (визард) → Стас. Discriminated union по `object_type` (`Literal` + `Field(discriminator=...)`): новый тип объекта — это новый `*Params`-класс и новое значение `ObjectType`, без изменений в matching/economics (они должны читать параметры через общие поля/теги, а не через ветвление по типу объекта).
5. **MatchResult** (`matching.py`) — Стас (matching) → фронт, econWrapper, simulation. `MatchCandidate.factors` — разбивка score по факторам для explainable-ranking; `selected_equipment` — финальный состав оборудования, общий вход для расчёта экономики и симуляции. Движок реализован в `Project/backend/matching/`, см. раздел «Подбор и ранжирование: matching» ниже.
6. **Scene** (`topology.py`) — Алексей (редактор плана, `frontend/src/features/planEditor`) → Артём/Стас (matching), Стас (simulation), Владимиров (хранение). 2D-сцена: зоны, стены, маршруты, точки операций/зарядки, стартовые позиции роботов. Файл называется `topology.py` по историческим причинам, но с 2026-09-22 — pydantic-зеркало `Project/scene.md` (v1.2, включая `walls`); при изменении `scene.md` синхронизируй `topology.py`/`topology.md` вручную (детали — в `topology.md`).
7. **SimulationTimeline** (`simulation.py`) — Стас (simulation) → Алексей (редактор плана / viewer3d). Таймлайн считается один раз на бэкенде и просто проигрывается на фронте — без физики в браузере (см. ограничение по времени пересчёта в разделе НФТ).
8. **ScenarioInput/EconomicsResult** (`economics.py`) — Стас (econWrapper) → Владимиров. API-обёртка вокруг `EconInput`/`EconOutput`; не путать `EconomicsResult` (контракт 8, pydantic, для API/фронта) с `EconOutput` (контракт 3, dataclass, внутренний расчёт).
9. **ProjectRecord** (`records.py`) — Владимиров (backend-glue) ↔ БД, → фронт. Версионирование — полными снапшотами: `ProjectVersion` целиком включает `project_input`/`topology`/`match_result`/`scenarios`, чтобы открыть старую версию проекта значило увидеть те же входные данные и тот же результат, а не пересчитать по текущим формулам/каталогу.

Общие соглашения по всем контрактам:

- `enums.py` — единственное место общих перечислений. Новый тип объекта/решения/сценария добавляется как новое значение enum, а не как правка существующих моделей — это и есть механизм расширяемости без переработки ядра (п. 4.2.6 ТЗ).
- Каждый `contracts/<name>.py` имеет парный `contracts/<name>.md` — таблица полей (тип/обязательность/дефолт/описание) для чтения не-питонистами команды. При изменении модели обновляй оба файла.

## Редактор плана: откуда он взялся

Раньше новые версии 2D-редактора приходили незакоммиченной папкой `ЛЦТ/` в корне (дистрибутив
«для одного клика», который Алексей собирал у себя) и переносились в `Project/.../editor2d/` с
архивацией прежней версии. С 2026-09-25 редактор — модуль визарда
`Project/frontend/src/features/planEditor/`, Алексей работает прямо в репозитории через ветку
`frontend` и PR; дропов `ЛЦТ/` больше не будет. Если такая папка всё же появится — это старая
копия, сверяй её с модулем, а не переноси целиком.

## Суть задачи

Веб-платформа для экспресс-предынвестиционной оценки роботизации: пользователь выбирает отрасль/объект, платформа подбирает подходящие роботизированные решения, считает экономику (CAPEX/OPEX/TCO/ROI/срок окупаемости) и визуализирует работу роботов на 2D-схеме объекта, чтобы подтвердить расчетную производительность. Платформа не заменяет полноценное ТЭО, а формирует обоснованную гипотезу и материалы для перехода к нему.

Целевая аудитория: руководители предприятий, технические директора, руководители по автоматизации/цифровой трансформации, логисты, операционные/финансовые аналитики.

Обязательное требование архитектуры (сквозное для всех разделов ниже): модель данных и расчетные модули должны допускать добавление новых отраслей, типов объектов, параметров и роботизированных решений **без переработки ядра системы**.

## Пользовательский путь (сквозной сценарий)

1. Выбор отрасли и объекта (склад / аэропорт / медицинское учреждение — минимум один тип на хакатон, либо другой тип на выбор команды).
2. Ввод параметров объекта вручную или загрузка Excel/CSV по шаблону, с валидацией форматов, обязательности и диапазонов.
3. Подбор решений — платформа показывает применимые продукты и объясняет причины включения/исключения (explainable ranking, а не черный ящик).
4. Сравнение решений по унифицированным характеристикам.
5. Расчет экономики: состав оборудования, CAPEX, OPEX, TCO, годовой эффект, срок окупаемости, ROI — с показом исходных формул и допущений.
6. What-if анализ: минимум 3 сценария в одной таблице (базовый без роботизации + минимум 2 сценария роботизации — покупка и услуга/аренда).
7. Визуализация: 2D-схема объекта с зонами, маршрутами, роботами, точками операций и зарядки; визуализация должна подтверждать расчетную производительность, а не быть декоративной.
8. Сохранение проекта и экспорт отчета в PDF + расчетов в Excel/CSV, с возможностью повторного открытия и воспроизведения расчета (версионирование исходных данных и модели).

Роли: гость (каталог + демо-расчет без сохранения чувствительных данных), зарегистрированный пользователь (проекты, ≥3 сценария на проект), администратор (управление каталогом, справочниками, нормативами). Роль вендора — опционально.

## Минимальный состав входных параметров по типам объектов

- **Склад**: площадь и рабочие зоны; режим работы; объем входящих/внутрискладских/исходящих операций; тип хранения; количество SKU; масса и габариты грузовой единицы; численность и стоимость персонала; текущая производительность; протяженность маршрутов; доступная площадь и ограничения планировки.
- **Аэропорт**: тип и зона операции; режим работы; пассажиро-/грузопоток; количество операций и пиковая нагрузка; протяженность маршрутов; масса/габариты объектов; численность персонала; требования безопасности; закрытые/открытые зоны.
- **Медицинское учреждение**: тип учреждения; площадь и этажность; режим работы; объем перевозок (грузы, белье, питание, медикаменты, отходы); маршруты и лифты; санитарные требования; численность персонала; ограничения доступа/безопасности.

Состав полей расширяем — но расширение не должно усложнять базовый пользовательский путь.

## Каталог решений

- Иерархия: отрасль → тип объекта → процесс → тип роботизированного решения → конкретный продукт.
- Обязательные группы характеристик на каждый продукт: идентификация (производитель, наименование, тип, назначение, страна, статус доступности), технические характеристики (грузоподъемность, габариты, скорость, производительность, автономность, точность позиционирования, тип навигации, условия эксплуатации), инфраструктура (покрытие/проходы, зарядка, связь, интеграция, сервис), экономика (ориентировочная стоимость оборудования/ПО/внедрения/обслуживания, модель приобретения, срок службы), применимость (поддерживаемые процессы/объекты, ограничения, кейсы), качество данных (источник, дата актуализации, полнота/подтвержденность).
- Ручное добавление/редактирование через админ-интерфейс обязательно; автопарсинг из открытых источников — преимущество, не замена.
- Хранить ссылку на источник, дату обновления и признак подтвержденности по каждой характеристике.
- Справочник типов роботизированных решений (для классификации каталога) из «Дополнений»: мобильные роботы (общая категория), AMR, FMR/автономные погрузчики, робот-штабелер, робот-тягач, робот-уборщик, беспилотный погрузчик, стационарные системы умного хранения (класс AutoStore).

## Подбор и ранжирование

- Правила фильтрации/исключения (по габаритам, массе, точности позиционирования, требованиям безопасности и т.д.) команда формирует и документирует самостоятельно — в ТЗ нет готового набора правил.
- Не рекомендовать решение при жестком несовместимом ограничении; при нехватке данных — помечать «требует проверки», а не скрывать.
- Ранжирование должно быть объяснимым: пользователь видит критерии и вклад факторов в итоговую оценку.
- Разрешено ручное добавление в сравнение решений вне автоподборки — с предупреждением.

### Подбор и ранжирование: matching (контракт 5, движок реализован)

`Project/backend/matching/`: `rules.py` (эвалюатор `CompatibilityRule` — путь через точку до поля `CatalogItem`/`ProjectInput`, операторы `eq/ne/lt/lte/gt/gte/in/has_tag`; правило срабатывает только если истинны ОБА условия — на оборудовании и на объекте; отсутствие данных на стороне оборудования при релевантном объекте даёт отдельный исход `UNKNOWN`, а не тихий пропуск — так и реализовано требование «при нехватке данных помечать «требует проверки»»), `category_rules.py` (второй, независимый вид правил — категориальные правила Артёма из `contracts/dictionaries/compatibility_tree.json`: дерево категорий оборудования `tree.nodes` + 87 правил `{from, to, type}` вида «amr нельзя underwater_work»; `CategoryTaxonomy.evaluate()` поднимается по цепочке родителей категории — правило на «mobile» действует и на её потомка «amr» — и сравнивает с релевантными для `ObjectType` задачами/средой; см. докстринг файла, почему это дополняет `CompatibilityRule`, а не заменяет: одно сравнивает числа/строки конкретного поля, другое — категории, которые числовым правилом не выразить), `scoring.py` (explainable score: 4 взвешенных фактора — совместимость 0.5 (оба вида правил, `CompatibilityRule` И `CategoryTaxonomy`, на один и тот же фактор — любой `forbidden`-вердикт с любой стороны обнуляет score и переводит кандидата в `excluded`), доступность решения 0.2, качество данных каталога 0.15, заявленная применимость к типу объекта 0.15; сумма `factors[].contribution` всегда равна итоговому `score`), `quantity.py` (оценка `quantity_if_selected` = пиковая нагрузка/час ÷ (`throughput_per_hour` каталога × коэффициент использования 0.85) — реализовано для всех трёх типов объектов, у медучреждения пиковая нагрузка выводится из `cargo_volume_per_day` через явно задокументированные допущения `MEDICAL_SHIFT_HOURS`/`MEDICAL_PEAK_LOAD_FACTOR`), `service.py` (`run_matching(project_input, catalog, rules, project_id=..., taxonomy=None) -> MatchResult` — точка входа; `taxonomy=None` лениво грузит `compatibility_tree.json` один раз на процесс), `fixtures.py`/`demo.py` (по умолчанию — реальный каталог `catalog.loader.load_catalog()`, флаг `--fixtures` — старый полностью иллюстративный демо-каталог, см. «Команды разработки»).

Каталог для matching теперь реальный: `Project/backend/catalog/loader.py` читает `Датасет/Датасет/catalog_export_v4.csv` (223 строки, но 36 из них — тот же физический продукт под другую отрасль/сценарий/кейс, схлопнуты в один `CatalogItem` на уникальный `id` — итого 187 позиций, см. коммит «Каталог: схлопнуть дубли id») в `CatalogItem` — `identification`/`economics.equipment_cost`/`applicability.case_studies` заполнены из колонок честно, `TechnicalSpecs` намеренно оставлен пустым везде (в CSV нет числовых ТТХ отдельными колонками, только иногда в свободном тексте названия — парсить регуляркой означало бы гадать), поэтому `data_quality.confidence = "unverified"` у каждой позиции. Итоговый статус (`recommended`/`needs_review`/`excluded`) при этом НЕ константа для всех кандидатов сразу: `excluded` даёт категориальный запрет (БАС/морская техника не для склада и т. п.), а `needs_review` против `recommended` зависит от того, задевают ли числовые `DEMO_RULES` конкретный `ProjectInput` — если условие на объекте не выполняется (например, проходы достаточно широкие), правило вообще не смотрит на отсутствующие ТТХ оборудования и статус может дойти до `recommended` по одним категориальным правилам; если выполняется — недостающие ТТХ дают `UNKNOWN` и статус падает до `needs_review`. `type_raw`/`subtype_raw` в `attributes` — по ним `CategoryTaxonomy.match_entity()` сопоставляет позицию каталога с деревом категорий Артёма (112/187 позиций опознаются, остальные — новые/не описанные им категории, тогда категориальная проверка нейтральна, а не запрещающая).

Открытые вопросы, требующие решения команды (не разрешены самостоятельно, т.к. это не техническая, а данные/продуктовая развилка):
1. **Отрасль → ObjectType не сопоставлена.** Колонка `Отрасль` в CSV (Торговля и услуги / Промышленность / Транспорт и логистика / ТЭК / Сельское хозяйство / Безопасность / Строительство / ЖКХ / Лесное хозяйство) не совпадает с нашими тремя `ObjectType` (warehouse/airport/medical) ни для одного значения напрямую — нужна классификация команды, а не автоматический вывод; пока `CatalogItem.applicability.supported_object_types` из загрузчика пустой (не про категорию — про заявленную применимость к объекту, отдельный фактор скоринга).
2. **Числового набора `CompatibilityRule` (габариты/масса/точность позиционирования) от Артёма всё ещё нет** — три правила в `matching/fixtures.py` остаются иллюстративными. Категориальные правила Артёма (`compatibility_tree.json`, 87 штук) уже подключены через `category_rules.py` — это закрывает другую половину совместимости (какая категория робота годится для какой среды/задачи), но не заменяет числовые пороги, которых ТЗ явно требует отдельно.
3. **Задачи Артёма покрывают только склад.** `_OBJECT_TYPE_TASKS` в `category_rules.py` — из 87 правил специфичные задачи (`warehouse_logistics`/`warehouse_inventory`) есть только под склад; аэропорт/медучреждение фильтруются пока только по общей среде (`outdoor`/`indoor`). Как только у Артёма появятся задачи вида `airport_ramp`/`hospital_logistics`, их нужно добавить в словарь — код переписывать не придётся.

## Экономическая модель

Минимальные рассчитываемые показатели: количество роботов и вспомогательного оборудования, CAPEX по укрупненным статьям, годовой OPEX и его изменение относительно базового сценария, чистый годовой экономический эффект, простой срок окупаемости, ROI, TCO на горизонте ≥5 лет.

Базовые зависимости (см. ТЗ п. 3.5.2):
- Количество роботов = пиковая потребность в операциях / эффективная производительность одного робота (с учетом загрузки, доступности, резерва).
- CAPEX = оборудование + инфраструктура + ПО + интеграция + пусконаладка + обучение + резерв.
- OPEX = сервис + лицензии + электроэнергия + связь + расходники + ремонт + персонал эксплуатации.
- Годовой эффект = сокращение текущих затрат + доп. доход/предотвращенные потери − доп. OPEX.
- Срок окупаемости = CAPEX / годовой эффект (при эффекте > 0).
- ROI = накопленный эффект за период / CAPEX × 100%.
- TCO = CAPEX + сумма OPEX за расчетный горизонт с учетом замены компонентов.

Уточнения из «Дополнений к ТЗ» (раздел 2):
- Базовый сценарий финансирования — собственные средства; заемное финансирование (кредит/лизинг) — опционально, со своей ставкой, графиком платежей и обслуживанием долга.
- Рекомендуется учитывать амортизацию CAPEX (метод и срок службы — на усмотрение команды, но одинаково внутри проекта).
- Точный состав статей CAPEX/OPEX команда определяет сама и фиксирует в допущениях — важна согласованность между расчетной моделью и демо-датасетами.
- Сценарий «роботы как услуга» (RaaS): структура платежей, срок контракта, распределение CAPEX/OPEX — полностью на усмотрение команды, но должен быть сравним с базовым и с покупкой по единым метрикам.
- Все формулы, допущения, единицы измерения и источники обязаны быть видны пользователю в интерфейсе/отчете — недокументированные коэффициенты запрещены.
- Обязательна чувствительность результата минимум к 3 параметрам на сценарий (например, стоимость оборудования, объем операций, стоимость труда); пользователь может менять ключевые допущения (стоимость персонала, режим работы, производительность, стоимость оборудования/обслуживания, коэффициент загрузки, горизонт расчета).
- Рекомендация о целесообразности — не жесткий порог, а числовой результат + риски + интерпретация (например, интервалы <3 лет / 3–5 лет / >5 лет).

## Имитация и визуализация

- Только 2D (3D — необязательный бонус). Отображать зоны, маршруты, роботов, точки операций и зарядки.
- Визуализация должна использовать параметры выбранного сценария и подтверждать расчетную производительность (загрузка оборудования, простои, узкие места) — не быть чисто декоративной анимацией.
- Управление: запуск/остановка/перезапуск, изменение скорости воспроизведения, выбор сценария.

## Экспорт и отчетность

- Итоговый дашборд сравнения сценариев с кратким заключением.
- Отчет: параметры объекта, выбранные решения, состав оборудования, расчет экономики, ограничения, источники данных, дата расчета; явная пометка, что результат — предварительная оценка, требующая верификации.
- Экспорт отчета в PDF, таблиц в Excel/CSV, экспорт/сохранение визуализаций.

## Нефункциональные требования и стек

- Веб-приложение с разделением клиент/сервер; технологический стек свободный (предпочтительно open source).
- Обязателен Docker: Dockerfile + docker-compose.yml (или эквивалент) для воспроизводимого запуска.
- БД: реляционная или документоориентированная.
- При наличии API — документировать, желательно спецификацией OpenAPI.
- Конкурсная версия должна работать полностью на заранее загруженных данных — внешние источники не могут быть единственной точкой отказа демо.
- Производительность: каталог/формы/проекты без заметных задержек при ≤50 одновременных пользователях; расчет экономики ≤10 сек; запуск/пересчет имитации ≤60 сек с индикацией статуса; ошибки загрузки данных не должны приводить к потере сохраненного проекта.
- Безопасность: разграничение доступа по ролям, пароли не в открытом виде, изоляция проектов между пользователями, HTTPS при сетевом размещении, без реальных ПДн в демо-данных, возможность удаления проекта и его файлов.
- UI: русскоязычный, понятный без инструкции, единицы измерения/подсказки/примеры в полях, понятные тексты ошибок со способом исправления, корректная работа от разрешения 1366×768.

## Критерии оценки (вес)

Подход к решению — 15%; техническая проработка (архитектура, воспроизводимость, модель данных, производительность) — 25%; соответствие ТЗ (полнота пути: каталог/подбор/расчет/сравнение/визуализация/сохранение/экспорт) — 25%; эффективность решения (обоснованность расчетов, объяснимость рекомендаций, качество визуализации, масштабируемость) — 25%; питч-сессия — 10%. Плюсом идут: автообновление каталога, ML/оптимизация при обоснованной задаче, интеграционные API, расширенная чувствительность расчетов, детальная модель нескольких типов объектов, качественная фиксация происхождения данных.

## Что команда обязана проработать и задокументировать сама (не задано в ТЗ)
