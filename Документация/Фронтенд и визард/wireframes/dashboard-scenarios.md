# Макет: итоговый дашборд сравнения сценариев

Черновой вайрфрейм — расположение блоков и логика чтения, не дизайн.
Маршрут: `/projects/:id/dashboard`. Данные: `EconomicsResult[]` (контракт
[economics.md](../../contracts/economics.md)), минимум 3 сценария по ТЗ.

Базовое разрешение — **1366×768**. Живой макет: `/wireframes/dashboard` в
приложении (`frontend`).

## Что должно быть видно без прокрутки

При 768 px высоты «над сгибом» помещается: шапка 56 + шапка проекта 48 +
панель действий 48 + строка KPI 92 + **таблица сравнения ~500**. То есть
главный ответ — «какой сценарий выгоднее и за сколько окупится» — виден
сразу, без скролла. Графики, чувствительность и допущения — ниже.

По горизонтали: колонка показателя 260 + до 4 колонок сценариев по 250.
Пятый и далее — горизонтальная прокрутка **внутри таблицы**, первая колонка
закреплена. Страница по горизонтали не скроллится никогда.

## Блоки

**1. Панель действий (48 px).** Переключение «Дашборд / Отчёт / Визард»,
выбор горизонта (`horizon_years`, от 5 лет по ТЗ — смена горизонта требует
пересчёта, показываем это явно), «Пересчитать», «Экспорт» (PDF / Excel).

**2. Строка KPI (92 px).** Четыре плитки — ответ на главный вопрос до всякой
таблицы. Лучший сценарий определяется по минимальному `payback_years` среди
не-базовых; если у всех `payback_years = null` (эффект ≤ 0) — плитка честно
пишет «Ни один сценарий не окупается на горизонте 5 лет» и подсвечивает это
как результат, а не как ошибку.

**3. Таблица сравнения.** Показатели — строки, сценарии — колонки: так
взгляд идёт по строке и сравнивает одно и то же между сценариями.
`baseline` всегда первый и визуально отделён — это точка отсчёта, а не
конкурент. Раскрываемые строки для `capex_breakdown` и `opex_breakdown`
(по умолчанию свёрнуты — иначе 15 строк вместо 8). ★ отмечает лучшее
значение в строке. Колонка `custom`-сценария удаляется, остальные — нет.

**4. Графики.** Накопленный денежный поток с точкой безубыточности —
единственная картинка, которая объясняет разницу «дорого, но окупается» и
«дёшево, но не окупается». Структура затрат — по выбранному сценарию,
переключатель CAPEX/OPEX.

**5. Чувствительность.** `sensitivity: list[SensitivityResultPoint]`,
минимум 3 параметра по ТЗ. Формат «было → стало» вместо абсолютных чисел:
читателю важна устойчивость вывода, а не новое число.

**6. Допущения.** `assumptions_note` — по ТЗ обязательны к показу. Свёрнуты
до 3 строк, но **на странице, а не в модалке**: в PDF они попадают тем же
блоком.

## Поведение

| Ситуация | Что показываем |
|---|---|
| Сценариев меньше 3 | Таблица + карточка-заглушка «Добавьте сценарий для сравнения» со ссылкой на шаг 6 |
| `payback_years = null` | «Не окупается» + пояснение «годовой эффект ≤ 0», а не прочерк |
| Параметры изменились после расчёта | Жёлтая плашка над KPI: «Входные данные изменились 19.09 — показан расчёт от 18.09» + «Пересчитать» |
| Идёт пересчёт (до 60 с) | Плашка с прогрессом, старые числа остаются видимыми и приглушены — экран не пустеет |
| Открыт снапшот старой версии | Красная полоса «Версия 2 от 10.09, только для чтения» + «Вернуться к текущей» |
| Экспорт | PDF = печатная вёрстка `/projects/:id/report`; Excel = таблица сравнения + разбивки + чувствительность |

## Открытые вопросы

1. Накопленный денежный поток по годам — в `EconomicsResult` его нет (есть
   только `tco_total`, `annual_effect`). Либо фронт строит линейно из
   годового эффекта (грубо), либо нужна серия по годам в контракте.
   **Предложение: добавить `cashflow_by_year: list[float]`.**
2. Сравнение сценариев из **разных версий** проекта (было/стало) — нужно ли
   в MVP? Сейчас дашборд показывает сценарии одной версии.
3. Лучший сценарий по окупаемости или по TCO? Сейчас по окупаемости, но у
   RaaS окупаемость всегда лучшая при худшем TCO — возможно, нужны обе
   плитки-«победителя».
