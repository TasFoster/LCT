## 1. Итог

| Вопрос | Решение |
|---|---|
| Кто ходит на сервер | Только визард (API-слой Владимирова). Редактор отдаёт и принимает готовый TS-объект `Scene` |
| Что сохраняем | `PUT /api/projects/{id}/input` — параметры формы, `PUT /api/projects/{id}/scene` — план. Одна запись проекта, не две сущности |
| Подложка-чертёж | Отдельная ручка `POST /api/projects/{id}/scene/background`, в плане остаётся только `image_url` |
| Предупреждения по плану | Считает сервер и отдаёт вместе со сценой. Редактор подсвечивает по `target_id`, свои проверки не выдумывает |
| Справочник | Один на всех: `categories.json` (генерируется из книг Артёма) + `form_options.json` (справочники форм, ведётся руками) |
| Стоимость персонала | Как в ТЗ: `staff_cost_per_month` — за **весь** замещаемый персонал в месяц, не на одного |
| Аэропорт без площади | Черновик стандартного размера 100 × 60 м, пользователь растягивает границы сам |

## 2. Дизайн: один продукт, а не два сайта

Редактор открывается внутри шага 7, между степпером и кнопками визарда.
Чтобы это не выглядело вставленным чужим приложением:

- **Цвет, шрифт, скругления, тени** — из токенов дизайн-системы фронтенда
  (`Project/frontend/src/shared/styles/tokens.css`), включая тёмную тему.
  Своих цветов редактор не заводит.
- **Раскладка**: слева рейка инструментов 48 px, справа панель свойств 264 px,
  между ними — холст. Шапку, степпер, статус сохранения, кнопки
  «Сохранить план» / «Далее» рисует визард — редактору их дублировать не нужно.
- **Размер**: рабочая область рассчитана на 1366 × 768 (НФТ). На такой высоте
  на холст остаётся ~400 px, поэтому высота редактора эластичная
  (`min-height: 400px`), а панель свойств прокручивается внутри себя.
- **Технически** — модуль того же React-проекта, а не iframe: общие токены,
  общий роутер, общий стейт, нет проблем с размером и фокусом. Редактор
  переехал в `src/features/planEditor/` (2026-09-25) и экспортирует один
  компонент `PlanEditor` с пропсами ниже.

## 3. Интерфейс встраивания

```ts
// Project/frontend/src/features/planEditor/types.ts
interface PlanEditorProps {
  value: Scene | null;                    // null — плана ещё нет (черновик проекта)
  onChange: (plan: Scene) => void;        // каждое изменение; на сервер ходит визард
  context: {
    objectType: 'warehouse' | 'airport' | 'medical';
    areaSqm: number | null;               // из формы, для масштаба и проверок
    routeLengthM: number | null;
    workingZoneIds: string[];             // из формы, id из categories.json → working_zones
    robots: { catalog_item_id; name; category_id; quantity }[]; // из состава оборудования
    minAisleWidthM: number | null;        // самый требовательный к проходу робот
  };
  categories: Categories;                 // единый справочник целиком
  warnings: SceneWarning[];               // проверки сервера по последнему сохранению
  onUploadBackground: (file: File) => Promise<void>;
  width: number;                          // область, выделенная визардом, px
  height: number;
  readOnly?: boolean;                     // открыт старый снапшот версии
}
```

Правила:

- Редактор **не ходит на сервер**. Сохранение, статус, ошибки и конфликты — у визарда.
- Редактор **не хранит свой справочник**, берёт `categories` из props.
- Стартовое состояние: если `value === null`, визард предлагает «Черновик из
  параметров» — контур здания по площади, зоны по рабочим зонам из формы,
  точки операций, зарядка и роботы у неё
  (`features/planEditor/autoLayout.ts`, на выходе обычная `Scene`). Редактор
  может взять его за основу, а не начинать с пустого холста.
- В `StepTopology.tsx` стоит сам редактор — `PlanEditor` из
  `features/planEditor` (временный `PlanEditorStub` с тем же интерфейсом
  удалён 2026-09-25).

## 4. Что уходит на сервер

### Параметры формы — `PUT /api/projects/{id}/input`

Сохраняются на шаге 2 и при каждом изменении. Тело — `ProjectInput`
(контракт 4) плюс версия записи, по которой клиент правил данные.

### План — `PUT /api/projects/{id}/scene`

Тело — `Scene` (контракт 6) плюс та же версия. Визард дополнительно передаёт,
по какой версии параметров рисовался план: если параметры успели поменять,
план помечается устаревшим, и визард показывает «параметры менялись после
этого плана».

### Подложка — `POST /api/projects/{id}/scene/background`

`multipart/form-data`, ответ `{ image_url }`. В `Scene.site.background`
кладётся только ссылка: скан весит мегабайты, гонять его вместе со сценой не
нужно, а `data:`-URL из редактора API-слой обязан подменить на `image_url`
перед сохранением (см. `scene.md`, раздел Background).

### Что ждём в ответ

Сейчас мок (`features/projectApi/mockServer.ts`) отдаёт на каждый `PUT`
состояние всей записи проекта: номер версии, состояние каждой части
(`missing` / `saved` / `stale`), время сохранения, предупреждения по плану,
чего не хватает для расчёта. Форма ответа описана в
`Project/frontend/src/shared/api/projectState.ts` — **это предложение
фронтенда, а не утверждённый контракт**: когда появится бэкенд, форму
фиксируем вместе и мок убираем.

Чего мок уже придерживается и что хотелось бы сохранить в реальном API:

- **409** — если присланная версия записи не совпала с серверной (проект
  правили в другой вкладке). Визард перезагружает состояние и просит повторить.
- **422** — список ошибок по полям (`path`, `code`, `message`), а не общий текст.
- План без параметров не принимается: план привязан к параметрам объекта.
- Шаг 7 необязательный — проект без плана это нормальный черновик, а не ошибка.

### Предупреждения по плану

Считает сервер, отдаёт вместе со сценой, эталонная реализация —
`features/projectApi/sceneChecks.ts` (её можно повторить один в один):

| Код | Уровень | Когда |
|---|---|---|
| `route_crosses_wall` | error | маршрут пересекает стену |
| `robot_in_restricted_zone` | error | робот стоит в зоне ограниченного доступа |
| `aisle_too_narrow` | warning | маршрут ближе к стене, чем нужно выбранной технике |
| `zone_outside_bounds` | warning | зона выходит за габариты площадки |
| `route_not_linked` | warning | концы маршрута не привязаны к точкам (`RoutePoint.ref`) |
| `charging_capacity_exceeded` | warning | больше 4 роботов на одно место зарядки — будет очередь |
| `scene_area_differs_from_form` | info | площадь плана расходится с формой больше чем на 20 % |

## 5. Справочник: один на форму, план и редактор

Два файла в `Project/backend/contracts/dictionaries/`:

- **`categories.json`** — оборудование, рабочие зоны, виды точек, задачи, среды.
  Генерируется скриптом `Project/tools/categories_from_xlsx.py` из книг Артёма,
  руками не правится. Это канон для редактора и для панели свойств.
- **`form_options.json`** — то, чего в книгах нет: справочники форм визарда
  (режимы работы, типы хранения, зоны аэропорта, санитарные требования,
  ограничения планировки…), цвета типов зон, габариты техники для отрисовки и
  привязка рабочих зон к типам объекта. Ведётся руками.

Фронтенд склеивает их в один объект `Categories`
(`src/shared/dictionaries/index.ts`) и отдаёт редактору целиком. У значений
есть `aliases`, поэтому и прежние английские id форм, и транслит из редактора
приводятся к одному id функцией `resolveId()` — переименовывать данные в уже
сохранённых проектах не нужно.

В данных храним **id**, подпись берём из справочника. Значение, которого в
справочнике нет, пользователь может вписать руками — оно сохраняется с
префиксом `custom:` и не ломает проверки.
