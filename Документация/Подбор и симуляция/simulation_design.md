## 0. Входные данные — важное уточнение по сцене

`backend/contracts/topology.py` (контракт 6) — устаревший черновик. Реальный контракт
сцены теперь — **`scene.md` / `scene.example.json` / `editor2d/src/scene/types.ts`**
(Алексей, готово). Симуляция должна читать именно эту структуру:
`Scene{site, zones, operation_points, charging_points, routes, robots}`, координаты —
метры, `y_down`. `backend/contracts/topology.py` нужно будет переписать под неё до
интеграции (см. п.6) — сейчас типы в contracts/ и то, что реально отдаёт редактор,
разные.

Кроме сцены, на вход идут:
- `MatchResult.selected_equipment` — состав флота (`catalog_item_id` → `quantity`).
- `CatalogItem.technical` — `speed_mps`, `throughput_per_hour`, `autonomy_hours`.
- `ScenarioInput`/`ProjectInput.params` — режим работы объекта, объёмы операций
  (для склада: `inbound/internal/outbound_ops_per_day`), `operating_hours_per_year`.

## 1. Парадигма: полная дискретно-событийная симуляция с очередью

Решено (не упрощённый циклический вариант): робот — конечный автомат с очередью
задач, реальной конкуренцией за проходы/зарядку, событийным циклом по времени.
Компромисс по сложности реализации принят осознанно — время расчёта не является
узким местом (см. п.4), узкое место — время разработки, но команда выбрала точность
модели.

## 2. Граф маршрутов и путь робота

Строится один раз при загрузке сцены:

- **Узлы графа** — вершины `Route.points`. Вершины разных маршрутов с одинаковыми
  координатами — один узел (правило из `scene.md`). Вершина с `ref` — узел этого
  узла-точки (`OperationPoint`/`ChargingPoint`), через него робот входит/выходит
  из графа в конкретную операционную/зарядную точку.
- **Рёбра** — соседние точки внутри `Route.points`; вес ребра = евклидово расстояние
  в метрах. `bidirectional: true` → ребро в обе стороны, иначе только в порядке
  списка.
- Время прохода ребра = длина / `catalog_item.technical.speed_mps` конкретного
  робота (у разных типов роботов разная скорость — граф общий, времена индивидуальные).
- Кратчайшие пути между всеми точками (operation + charging + стартовые позиции
  роботов) считаются один раз через Дейкстру (`heapq`, stdlib — граф маленький,
  десятки узлов, отдельная библиотека вроде networkx не нужна).
- Робот без `start_point_id` (стоит не на точке) — проецируется на ближайшую точку
  ближайшего ребра маршрута; этот довесок до графа — разовый прямой отрезок, дальше
  робот двигается только по графу.

## 3. Генерация задач

Симуляция сама не знает про склад/аэропорт/мед. учреждение — это скрыто за
маленьким адаптером на входе (сохраняет принцип «новый тип объекта — новые данные,
не новый код ядра»):

- Адаптер по `ObjectType` превращает объёмные показатели `ProjectInput.params`
  (напр. `inbound_ops_per_day` для склада) в набор абстрактных `TaskType{origin_point_id,
  destination_point_id, service_time_s}`, распределённых по операционным точкам
  сцены с подходящими `categories` (пока таксономии Артёма нет — по всем точкам
  поровну, задокументированное временное допущение).
- Моменты появления задач — **пуассоновский поток** (экспоненциальные интервалы
  между заявками) на каждую точку/тип задачи, с интенсивностью из объёмов ProjectInput.
- Генератор случайных чисел — `random.Random(seed)`, где `seed` — стабильный хэш от
  `scenario_id` (не от текущего времени!). Это даёт реалистичную стохастику и при
  этом воспроизводимость: тот же сценарий → тот же таймлайн, что требуется контрактом
  9 (`ProjectRecord`/`ProjectVersion` — открыл старую версию, увидел тот же результат).

## 4. Конечный автомат робота

Внутри `engine.py` стоит организовать автомат робота в три слоя, а не одним плоским
enum — это не меняет набор состояний ниже, только группирует их и разводит «какая у
меня задача» и «как я её физически выполняю»:

- **Lifecycle** («могу ли я вообще работать») — `is_available`; гейтит всё
  остальное. Сейчас источник False — только зарядка; при реализации отказов
  (см. §9 плана расширений) сюда же добавится `BROKEN`/`MAINT`.
- **Mission** («какую задачу выполняю») — текущий `TaskType` и его этап (к
  источнику → загрузка → к назначению → выгрузка → опционально зарядка); ставит
  цель нижнему слою (`goto`/`pickup`/`drop`), не управляет им напрямую.
- **Operational** («что делают моторы прямо сейчас») — конкретное состояние
  `RobotState` ниже; вызывает `Navigator`/граф из `graph.py`, двигается,
  публикует статус наверх после каждого этапа, а не только по завершении задачи.

Это же снимает часть открытого вопроса §8.4: Lifecycle=False (например, робот на
зарядке или гипотетически сломан) значит «не в пуле для назначения» независимо от
того, что физически стоит на сцене — источником истины по составу флота остаётся
`MatchResult.selected_equipment`, а Lifecycle лишь решает, кто из расставленных
роботов сейчас доступен.

Состояния — уже готовый `RobotState` (contracts/enums.py): `idle → moving → loading
→ moving → unloading → (moving → charging)? → idle`.

1. **IDLE** — диспетчер назначает роботу ближайшую (по графу) необслуженную задачу
   из общей очереди (жадный «ближайший свободный робот» — простое объяснимое
   правило, не ML, соответствует принципу explainable по ТЗ).
2. **MOVING** к точке-источнику задачи по кратчайшему пути.
3. **LOADING** на точке — фиксированная длительность обслуживания (`service_time_s`
   из адаптера задач, дефолт — из `throughput_per_hour` каталожной позиции, если
   задано, иначе документированная константа).
4. **MOVING** к точке-назначению.
5. **UNLOADING** — аналогично п.3.
6. Проверка заряда: остаток автономности = `autonomy_hours` минус наработка с
   последней зарядки. Если остатка не хватает на путь до `home_charging_point_id`
   с запасом — вместо следующей задачи робот едет заряжаться.
7. **CHARGING** на `ChargingPoint`: если есть свободный `slot` — заряжается
   (длительность — доля от `autonomy_hours`, документированный коэффициент допущения);
   если слотов нет — ждёт, это уже **BLOCKED**, естественный источник затора.
8. Возврат в IDLE, цикл повторяется до конца окна симуляции.

## 5. Конкуренция за ресурсы → узкие места (Bottleneck)

Три источника contention, все — из реальных данных контракта, без выдуманных
параметров:

- **Слоты зарядки** (`ChargingPoint.slots`) — впрямую из контракта, ничего
  досочинять не нужно.
- **Пропускная способность рёбер маршрута** — в `scene.md` нет ширины прохода,
  поэтому MVP-допущение: по умолчанию ребро пропускает робота не больше, чем один
  за раз, если у `Route` есть тег вроде `"narrow"`/`"single_lane"` (конвенция поверх
  существующего свободного поля `tags`, без правки контракта Алексея); иначе — мягкое
  ограничение через минимальную дистанцию следования. Робот, ожидающий освобождения
  ребра — BLOCKED.
- **Точка операции** — одновременно обслуживает одного робота (одно рабочее место).

После прогона по каждому ресурсу считается суммарное время ожидания; если оно
превышает порог от среднего времени цикла — попадает в `SimulationKPI.bottlenecks`
как `Bottleneck{location, description, severity}` (`medium`/`high` по величине
превышения).

## 6. Горизонт моделирования и кадры

- Симулируется **короткое представительное окно** (черновая оценка 30–60 мин
  модельного времени), а не весь режим работы объекта (может быть 24/7) — с
  коротким разогревом в начале, который не идёт в статистику (типовая практика
  discrete-event: пустая система в момент t=0 искажает метрики).
- `SimulationKPI` (`throughput_per_hour`, `utilization_pct`, `idle_time_pct`) —
  агрегаты за окно, throughput экстраполируется на час/смену. Компute-бюджет ≤60с
  тут не критичен — событий на десятки роботов за час модельного времени мало,
  считается на порядки быстрее лимита; ограничение по объёму — это объём кадров
  для фронта, не время расчёта.
- Кадры (`TimelineFrame`) пишутся событийно: при каждой смене состояния и при
  прохождении каждой промежуточной вершины графа во время MOVING (не только в
  начале/конце перегона) — иначе фронт, интерполируя линейно между двумя кадрами,
  срежет углы на изогнутом маршруте вместо движения точно по нарисованной ломаной.

**Замечание по контракту 7**: у `SimulationTimeline` сейчас нет поля под текстовое
пояснение допущений (аналог `EconomicsResult.assumptions_note`) — а окно+
экстраполяция и коэффициенты зарядки/пропускной способности ребра как раз надо
показать пользователю (ТЗ запрещает недокументированные коэффициенты). Нужно
добавить `assumptions_note: str` в `SimulationTimeline`, когда будем трогать контракт.

## 7. Предлагаемая структура модуля (`backend/simulation/`)

| Файл | Роль |
|---|---|
| `graph.py` | Граф из Scene.routes + точек, Дейкстра, кратчайшие пути |
| `tasks.py` | Адаптер ObjectType → TaskType, пуассоновский генератор заявок (сид от scenario_id) |
| `engine.py` | `World`: граф (из `graph.py`), очередь задач/диспетчер «ближайший свободный», список роботов, счётчики contention. Каждый робот — трёхслойный FSM (Lifecycle → Mission → Operational, см. §4). Событийный цикл, ресурсы/очереди/contention |
| `kpi.py` | Агрегация статистики ожидания → SimulationKPI + Bottleneck |
| `service.py` | Оркестрация: Scene + MatchResult + CatalogItem + ScenarioInput → engine → SimulationTimeline; точка входа для async-джобы |

## 9. Явные допущения (пойдут в `assumptions_note`, когда контракт получит это поле)

- Время обслуживания в точке операции — из `throughput_per_hour` каталожной позиции,
  если задано, иначе дефолт-константа (зафиксировать значение при реализации).
- Время полной зарядки — доля от `autonomy_hours` (коэффициент задать явно, не
  прятать в коде без комментария).
- Пропускная способность ребра маршрута по умолчанию не ограничена, кроме рёбер с
  тегом `narrow`/`single_lane` — временная конвенция до появления ширины прохода
  в контракте сцены.
- Диспетчеризация задач — «ближайший свободный робот», без оптимизации по батче
  задач (сознательно простое объяснимое правило, не решение задачи маршрутизации
  в общем виде).
- Окно моделирования (30–60 мин) и разогрев — представительное, не полный режим
  работы объекта; KPI экстраполируются.
